# m2.repo-understanding Run 2 (2026-01-22)

## Objectives
- Expand on "Next Research Thread #1" from 2026-01-21 overview by documenting watchdog + mpv subprocess behavior for troubleshooting docs.

## Findings (Observed)
- Watchdog calls originate from `surveillance.py`'s loop, which invokes `ScreenManager.run_watchdogs_active_screen()` once per `advanced.interval_check_status` seconds per monitor; only the active screen receives watchdog attention.
- `Screen.run_screen_watchdogs()` limits checks to streams that previously passed connectivity probes, keeping failed streams out of the restart loop until layout recalculation revisits them.
- `Stream.start_stream()` wraps every `mpv` launch in its own process group/session (Linux `setsid`, Windows `CREATE_NEW_PROCESS_GROUP`), records PID, and sets DISPLAY/screen geometry so later `wmctrl`/`xdotool` calls can manipulate the window reliably.
- `Stream.run_stream_watchdog()` relies on `Popen.poll()` to detect exits; on failure it feeds a newline to stdin, then calls `restart_stream()` which rebuilds the command and window state from cached coordinates.
- `Stream.stop_stream()` escalates to `SIGKILL` against the full group (or `terminate()` on Windows) before waiting, preventing zombie mpv children from surviving into the next rotation.

## Risks / Unknowns
- Hidden/cached screens never receive watchdog sweeps; if a stream dies shortly after caching, it can remain bad until rotation occurs.
- Immediate restarts on every failure could thrash unstable feeds; no per-stream cooldown/backoff exists yet.
- mpv stderr/stdout are not captured unless operators configure `--log-file` themselves, limiting built-in diagnostics.
