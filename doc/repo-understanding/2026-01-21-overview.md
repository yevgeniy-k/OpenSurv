# OpenSurv Repository Overview (2026-01-21)

## Purpose & Scope
- OpenSurv turns a commodity Linux/Windows host into a multi-monitor video wall with automatic stream recovery, rotation, and placeholder handling, targeting unattended surveillance or digital signage setups ([README.md#L1-L140](README.md#L1-L140)).
- Core expectations: watchdog-backed stream restarts, configurable layouts, dual-monitor awareness, and minimal manual coordinate management via YAML configs ([README.md#L42-L138](README.md#L42-L138)).

## Code Flow & Responsibilities
- **Entrypoint loop** – [surveillance/surveillance.py#L1-L154](surveillance/surveillance.py#L1-L154) bootstraps logging, reads `etc/general.yml`, enumerates physical displays via XRandR or pywin32, instantiates one `ScreenManager` per monitor, and runs the perpetual loop that: (a) polls keyboard input through Pygame, (b) rotates screens when their configured duration elapses, (c) periodically revalidates stream connectivity, and (d) triggers watchdog checks.
- **Monitor abstraction** – `get_monitors()` normalizes platform-specific monitor metadata (resolution, offsets, identifiers) and honors `advanced.monitor_allowlist` to limit which outputs spawn managers ([surveillance/surveillance.py#L15-L64](surveillance/surveillance.py#L15-L64)).
- **Screen orchestration** – [surveillance/core/ScreenManager.py#L11-L219](surveillance/core/ScreenManager.py#L11-L219) loads per-monitor configs from `etc/monitorN.yml`, initializes `Screen` objects, caches the “next” screen for instant swaps, and exposes operators such as `rotate_next()`, `force_show_screen()`, and `run_watchdogs_active_screen()`.
- **Screen lifecycle** – [surveillance/core/Screen.py#L14-L220](surveillance/core/Screen.py#L14-L220) manages layout math (columns → rows, placeholder tiles), probes stream availability unless suppressed, tracks active duration, and toggles visibility so cached screens can stay hidden until rotation.
- **Stream process management** – [surveillance/core/Stream.py#L17-L330](surveillance/core/Stream.py#L17-L330) encapsulates each camera/image feed: connectivity probes (RTSP OPTIONS, HTTP GET, filesystem checks), coordinate overrides, mpv command construction, watchdog restarts, and picture-in-picture overlays via `wmctrl` window state changes.
- **Rendering & Input** – [surveillance/core/util/draw.py#L1-L120](surveillance/core/util/draw.py#L1-L120) wraps a fullscreen Pygame surface per monitor, draws placeholders/overlays, captures keyboard events (quit, rotate, pause/resume, direct screen jumps), and keeps the pygame window focused via `ScreenManager.focus_background_pygame()`.

## Data & Configuration Model
- **Global settings** – [surveillance/core/util/config.py#L1-L4](surveillance/core/util/config.py#L1-L4) loads `etc/general.yml`, currently focusing on advanced timing, caching flags, and monitor selection ([surveillance/etc/general.yml#L1-L15](surveillance/etc/general.yml#L1-L15)).
- **Per-monitor layout** – Each `etc/monitorN.yml` declares `essentials.screens`: ordered screen definitions with `duration`, optional `nr_of_columns`, `disable_autorotation`, and stream lists (URL, `force_coordinates`, `imageurl`, `showontop`, mpv overrides, etc.) as illustrated in [surveillance/etc/monitor1.yml#L1-L140](surveillance/etc/monitor1.yml#L1-L140).
- **Runtime objects** – `ScreenManager` holds monitor metadata plus a list of `Screen` instances; `Screen` contains `Stream` objects with their process handles, coordinates, and watchdog state. Layout calculations derive bounding boxes $(x_1, y_1, x_2, y_2)$ for each stream based on monitor resolution and requested column count.

## External Interfaces & Dependencies
- **Video playback** – `/usr/bin/mpv` renders live streams; image streams use `core/util/image_viewer.py` with Pygame ([surveillance/core/Stream.py#L149-L260](surveillance/core/Stream.py#L149-L260)).
- **Display control** – `python-xlib` (Linux) or `pywin32` (Windows) discover monitors; `wmctrl`, `xdotool`, and `SDL` environment variables position windows ([surveillance/surveillance.py#L1-L64](surveillance/surveillance.py#L1-L64), [surveillance/core/Stream.py#L262-L330](surveillance/core/Stream.py#L262-L330)).
- **Health probes** – `socket`, `ffprobe`, and HTTP requests validate connectivity before attempting playback ([surveillance/core/Stream.py#L73-L205](surveillance/core/Stream.py#L73-L205)).
- **User input** – Pygame keyboard events drive rotation controls, quit, and direct screen selection ([surveillance/core/util/draw.py#L44-L108](surveillance/core/util/draw.py#L44-L108)).

## Risks, Gaps, & Questions
- **Linux-centric process tools** – `wmctrl`, `xdotool`, and reliance on X11 displays may fail on Windows deployments even though monitor detection now supports pywin32; need a feature parity review for window management ([surveillance/core/Stream.py#L214-L330](surveillance/core/Stream.py#L214-L330)).
- **Blocking probes** – Stream connectivity checks run sequentially and may block the main loop under slow networks; consider async probing or per-stream timeouts with better isolation ([surveillance/core/Screen.py#L74-L142](surveillance/core/Screen.py#L74-L142)).
- **Configuration validation** – YAML parsing currently assumes files exist and contain expected keys, lacking schema validation or error handling ([surveillance/core/ScreenManager.py#L27-L43](surveillance/core/ScreenManager.py#L27-L43)).
- **Platform abstraction** – Paths and binaries are hard-coded for Linux (`/usr/bin/mpv`, `/usr/bin/ffprobe`); Windows deployments require documented alternatives.
